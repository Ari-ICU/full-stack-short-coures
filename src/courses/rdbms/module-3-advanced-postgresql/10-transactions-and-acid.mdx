## 🛑 បញ្ហានៃការដំណើរការដោយគ្មានសុវត្ថិភាព

ស្រមៃថាអ្នកកំពុងសរសេរប្រព័ន្ធធនាគារ។ អតិថិជន A ផ្ទេរប្រាក់ $100 ទៅអតិថិជន B។ នេះតម្រូវអោយមានកូដ SQL ចំនួន ២ សកម្មភាព៖

```sql
-- ១. កាត់លុយពី A (ជោគជ័យ)
UPDATE accounts SET balance = balance - 100 WHERE id = 1;

--- 💥 ស្រាប់តែដាច់ភ្លើង ឬកូដ Error នៅត្រង់នេះ! 💥

-- ២. បន្ថែមលុយអោយ B (មិនបានដំណើរការ)
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
```

**លទ្ធផល:** លុយរបស់ A ត្រូវបានកាត់បាត់ ប៉ុន្តែលុយរបស់ B មិនកើនឡើងទេ។ លុយ $100 បានបាត់ពីប្រព័ន្ធ! នេះគឺជាមហន្តរាយដ៏ធំសម្រាប់ Database។

## 🛡️ អ្វីទៅជា Transactions?

ដើម្បីដោះស្រាយបញ្ហាខាងលើ RDBMS (ដូចជា PostgreSQL) បានបង្កើត **Transactions**។ Transaction គឺការចងកូដ SQL ច្រើនបញ្ចូលគ្នា ធានាថាវាត្រូវតែ **"ជោគជ័យទាំងអស់ ឫ បរាជ័យទាំងអស់"**។

ដើម្បីប្រើ Transaction យើងត្រូវស្គាល់ពាក្យ ៣៖
1. `BEGIN`: ចាប់ផ្តើម Transaction
2. `COMMIT`: បញ្ជាក់ថាជោគជ័យ ហើយរក្សាទុកទិន្នន័យជាអចិន្ត្រៃយ៍
3. `ROLLBACK`: បើមានបញ្ហា សូមបោះបង់ការកែប្រែទាំងអស់ ហើយត្រឡប់ទៅសភាពដើមវិញ

```rdbmsdiagram
RdbmsAcidDiagram
```

**ឧទាហរណ៍នៃការផ្ទេរប្រាក់ដែលមានសុវត្ថិភាព៖**

```sql
BEGIN; -- 🔒 ចាប់ផ្តើមចាក់សោរទិន្នន័យ

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

COMMIT; -- ✅ ជោគជ័យ ទិន្នន័យត្រូវបានរក្សាទុក!
```

ប្រសិនបើអ្នកកំពុងសរសេរកូដ ហើយដឹងថាមានអីខុសប្រក្រតី អ្នកអាចដំណើរការ៖
```sql
ROLLBACK; -- ❌ បោះបង់ចោលរាល់ការកែប្រែខាងលើទាំងអស់
```

> **ចំណាំសម្រាប់ Backend Developer:** ជាទូទៅ អ្នកមិនសរសេរពាក្យ `BEGIN` ឫ `COMMIT` ផ្ទាល់ទេ កម្មវិធី ORM (ដូចជា Prisma ឬ Eloquent) តែងតែមាន Function សម្រាប់រុំវាដោយស្វ័យប្រវត្តិ (ឧ. `prisma.$transaction()`) ប៉ុន្តែអ្នកត្រូវតែយល់ពីដំណើរការនៅពីក្រោយវា!

## 💎 ស្តង់ដារ ACID

តើអ្វីទៅដែលធ្វើអោយ Database ទូទៅ (ដូចជា Excel ឫ JSON file) ខុសពីប្រព័ន្ធ RDBMS ដូចជា PostgreSQL? នោះគឺស្តង់ដារ **ACID**:

1. **A - Atomicity (មិនអាចបំបែកបាន):** ប្រតិបត្តិការទាំងអស់ក្នុង Transaction តែមួយ ត្រូវតែជោគជ័យទាំងអស់ ឫបរាជ័យទាំងអស់ មិនមានពាក់កណ្តាលទី។
2. **C - Consistency (ភាពត្រឹមត្រូវ):** ទិន្នន័យតែងតែគោរពតាមច្បាប់ (Constraints) ដែលយើងបានកំណត់ មុននិងក្រោយពេល Transaction។ (ឧ. លុយមិនអាចអវិជ្ជមាន)។
3. **I - Isolation (ភាពឯកោ):** Transactions ច្រើនដែលដំណើរការក្នុងពេលតែមួយ (ឧ. មនុស្សពីរនាក់ទិញអីវ៉ាន់ចុងក្រោយតែមួយដំណាលគ្នា) នឹងមិនរំខាន ឬទាញយកទិន្នន័យខុសគ្នានោះទេ។ ប្រព័ន្ធនឹងតម្រង់ជួរពួកវា (Concurrency control)។
4. **D - Durability (ភាពយូរអង្វែង):** នៅពេលដែល `COMMIT` បានជោគជ័យហើយ ទិន្នន័យនោះនឹងមិនបាត់បង់ឡើយ ទោះបីជា Server ដាច់ភ្លើងភ្លាមៗក៏ដោយ (ព្រោះវាត្រូវបានសរសេរចូល Hard drive រួចរាល់)។
